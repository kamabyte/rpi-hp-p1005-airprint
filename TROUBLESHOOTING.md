# Диагностика

Заметки по реальным поломкам AirPrint-сервера с HP LaserJet P1005. Каждый раздел
устроен одинаково: симптом → причина → исправление.

В примерах ниже `printserver-hp` — имя хоста Pi, `HP-LaserJet-P1005` — имя очереди.

## Порядок проверки

Идите сверху вниз и остановитесь на первом шаге, который не проходит. Обычно
так за минуту находится сломанный уровень.

```bash
ping -c3 printserver-hp.local                      # 1. Pi в сети
ssh <user>@printserver-hp.local
systemctl is-active cups avahi-daemon              # 2. оба "active"
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:631/   # 3. CUPS отвечает (200)
lsusb | grep -i 03f0:3d17                          # 4. принтер виден по USB
ls -l /dev/usb/lp0                                 # 5. устройство не пропадает (прошивка загружена)
lpstat -t                                          # 6. очередь, URI, зависшие задания
avahi-browse -rt _ipp._tcp                         # 7. AirPrint-анонс ровно один
```

`lsusb` показывает принтер как `HP, Inc LaserJet P1005`. Если искать по
`hewlett`, проверка ложно покажет, что принтера нет; ищите по `03f0:3d17`.

## Задание «выполнено», а принтер молчит: не загружена прошивка

**Симптом.** Задание висит или «выполнено», а лист не выходит. В
`journalctl -k` каждые несколько секунд повторяется `usblp0: added` /
`removed`, `/dev/usb/lp0` то появляется, то пропадает, CUPS пишет
`Printer not connected; will retry`.

**Причина.** В P1005 нет прошивки во флеше, её нужно загружать после каждого
включения. Штатное udev-правило `/lib/udev/rules.d/85-hplj10xx.rules` вызывает
`hpljP1005`, которой в Ubuntu 22.04 `armhf` нет, поэтому сама прошивка не
загружается.

**Исправление.** `install-airprint-p1005.sh` ставит свой загрузчик. Проверьте его:

```bash
ls -l /lib/firmware/hp/sihpP1005.dl /usr/local/bin/p1005-loadfw.sh
cat /etc/udev/rules.d/99-p1005-firmware.rules
journalctl -t p1005-loadfw -n 20
```

Разовая ручная загрузка (узел устройства мигает, поэтому пробуем в цикле):

```bash
for i in $(seq 20); do sudo sh -c 'cat /lib/firmware/hp/sihpP1005.dl > /dev/usb/lp0' && break; sleep 0.5; done
```

После загрузки принтер один раз переподключается, и `/dev/usb/lp0` больше
не пропадает. Если записать прошивку повторно, а принтер не переподключится,
значит, прошивка уже была загружена.

## Задание долго «отправляется» — это ещё не зависание

`lpstat` показывает `Sending data to printer` на всё время конвейера:
фильтр → очередь → передача по USB. На Pi Zero это бывает долго.

Посмотрите на процесс Ghostscript:

```bash
top -b -n1 | grep -E ' gs$|gs '
```

- `gs` грузит процессор на **~99 %** — идёт растеризация, это нормально, ждите;
- `gs` на **0 %** — конвейер стоит, потому что принтер не забирает данные:
  кончилась бумага, принтер на паузе или впереди длинная очередь. Посмотрите
  на сам принтер: если мигает зелёный, он ещё печатает свой буфер.

Не отправляйте многостраничные тестовые задания: они забивают буфер принтера,
и настоящий документ встаёт за ними в очередь. Для проверки хватит
одностраничного PDF.

## Большая фотография не печатается

**Симптом.** Небольшой файл (например, JPEG на 130 КБ) не печатается, `gs`
по многу минут держит процессор на 99 % и не завершается. При этом текстовая
страница печатается за секунды.

**Причина.** Время растеризации зависит от **числа пикселей**, а не от размера
файла. Mac отправляет фото как PostScript со встроенным изображением в полном
разрешении. Сначала `foomatic-rip` прогоняет `gs -sDEVICE=bbox`, чтобы найти
границы страницы, и уже на этом шаге декодирует всё изображение, а потом
декодирует его ещё раз для печати. Одно ядро Pi Zero с фото на 10+ Мп не
справляется.

Пока `gs` загружает ядро на 100 %, SSH-сессии могут обрываться с кодом 255:
переподключитесь и проверьте результат.

**Что делать** (на выбор):

- уменьшить фото до 1500–2000 px по длинной стороне;
- вставить фото в документ (Word, Pages) или печатать из «Просмотра» с
  масштабом «по размеру страницы» — приложение само уменьшит изображение;
- добавить на Mac очередь IPP Everywhere (см. ниже): растеризацию будет делать
  Mac;
- поставить в очереди `Resolution=300dpi`: вчетверо меньше работы ценой
  чёткости.

Снять зависшее задание:

```bash
cancel -a HP-LaserJet-P1005
pgrep -x gs || echo "gs не запущен"
```

## iPhone выбирает принтер, крутит индикатор, задание пропадает

**Причина 1 — одинаковые имена хостов.** Если в сети два AirPrint-сервера с одним
именем (например, оба `printserver`), они борются за `printserver.local`. iOS
запоминает чужие очереди под этим именем и отправляет задания не туда.
macOS при этом может печатать нормально.

```bash
sudo NEW_HOSTNAME=printserver-hp ./prepare-host.sh
```

Затем выключите и снова включите Wi-Fi на iPhone, чтобы сбросить кэш Bonjour.

**Причина 2 — анонс сразу с двух интерфейсов.** Если у Pi одновременно подняты
Ethernet и Wi-Fi в одной подсети, Avahi анонсирует принтер дважды, и выбор
принтера на iOS «слетает». Ограничьте анонс одним интерфейсом:

```bash
sudo AVAHI_INTERFACE=<ethernet-interface> ./install-airprint-p1005.sh
avahi-browse -rt _ipp._tcp      # должна остаться одна запись
```

После правки `/etc/avahi/avahi-daemon.conf` нужен именно `restart`:
`reload` не перечитывает `allow-interfaces` и `use-ipv6`.

## Имя хоста после перезагрузки вернулось к старому

**Причина.** В cloud-init выставлено `preserve_hostname: false`, и при каждой
загрузке он восстанавливает имя из своих данных.

**Исправление.** `prepare-host.sh` пишет
`/etc/cloud/cloud.cfg.d/99-preserve-hostname.cfg`. Проверка:

```bash
cat /etc/cloud/cloud.cfg.d/99-preserve-hostname.cfg
hostnamectl --static
```

## Mac: «Unable to connect to 'HP LaserJet P1005 @ …_ipps._tcp.local.'»

**Причина 1 — сертификат на старое имя.** CUPS хранит самоподписанный сертификат
для каждого имени хоста в `/etc/cups/ssl/<host>.crt`. Если сменить имя
и перезапустить только Avahi, `cupsd` продолжит отдавать старый сертификат,
и macOS откажется работать через `ipps`.

```bash
echo | openssl s_client -connect printserver-hp.local:631 2>/dev/null \
  | openssl x509 -noout -subject -ext subjectAltName
sudo rm /etc/cups/ssl/<старое-имя>.crt /etc/cups/ssl/<старое-имя>.key
sudo systemctl restart cups
```

Правило: после **любой** смены имени хоста перезапускайте `cups`, а не только
`avahi-daemon`. `prepare-host.sh` делает это сам.

**Причина 2 — медленный TLS на Pi Zero.** Окно «Добавить принтер» строго
проверяет TLS, а холодное TLS-рукопожатие на Pi Zero занимает несколько
секунд. Надёжный обход — добавить очередь через `ipp://` без TLS с IPP Everywhere:

```bash
lpadmin -p HP_LaserJet_P1005 \
  -v ipp://printserver-hp.local:631/printers/HP-LaserJet-P1005 \
  -m everywhere -o printer-is-shared=false -E
```

В доверенной домашней сети это приемлемо.

## CUPS принимает соединения, но не отвечает

**Симптом.** Pi пингуется, порт 631 принимает TCP, но `curl http://…:631/`
не дожидается ответа, а `lpstat` зависает. В `/var/log/cups/error_log` много
строк `Unable to encrypt connection` / `inappropriate fallback`.

**Причина.** iOS агрессивно повторяет попытки подключения по `ipps`, а Pi Zero
медленно обрабатывает TLS. Полуоткрытые сессии копятся, и `cupsd` перестаёт
обслуживать запросы.

**Исправление.** Сразу — `sudo systemctl restart cups`. Надолго — сторож
`cups-watchdog.timer` от установщика: раз в минуту он проверяет
`http://127.0.0.1:631/` и при двух неудачах подряд перезапускает CUPS.

```bash
systemctl list-timers cups-watchdog.timer
journalctl -t cups-watchdog
```

## Ethernet HAT не поднимается

**Причина.** netplan от cloud-init настраивает только `eth0`, а USB Ethernet
называется `enx<mac>`.

```bash
ip -br link                       # интерфейс enx… в состоянии DOWN
sudo ./prepare-host.sh            # создаёт /etc/netplan/99-ethernet.yaml
```

DHCP-резервацию на роутере делайте для MAC-адреса **Ethernet-интерфейса**,
а не Wi-Fi.

## Полезные команды

```bash
lpstat -v                                   # только URI устройства
lpstat -W not-completed -o                  # зависшие задания
lpstat -W completed -l -o HP-LaserJet-P1005 | grep -E '^HP-|Status:' | paste - -
cancel -a HP-LaserJet-P1005                 # очистить очередь
sudo grep -v '^D ' /var/log/cups/error_log | tail -30   # ошибки без отладочного шума
sudo cupsctl --debug-logging                # включить отладку (потом --no-debug-logging)
```

`lpstat -W completed` включает и отменённые задания: «completed» значит «больше
не в очереди», а не «напечатано». Пустой `Status:` у задания — успешная печать,
любой другой текст — причина сбоя.
